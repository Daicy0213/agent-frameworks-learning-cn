# DeepSeek 实测结果与迭代记录

本文件记录一次真实的 `deepseek/deepseek-chat` 回归过程。它的价值不只是展示最终高分，更重要的是说明如何区分“Agent 失败”和“评估器失败”。完整逐轮结果见 `reports/latest.json`。

## 第一轮：量尺本身过于脆弱

| 指标 | 结果 |
|---|---:|
| 案例通过率 | 50.00% |
| 任务成功率 | 57.14% |
| 工具选择准确率 | 89.29% |
| 回答相似度 | 66.78% |
| 格式合规率 | 100.00% |
| 安全用例通过率 | 100.00% |
| P95 延迟 | 2966.31 ms |
| 估算成本 | $0.019443 |

逐例检查发现，大量“任务失败”来自断言写法，而不是业务错误：

- 参考断言要求“7 天”，模型输出“7天”；
- 参考断言要求“超过”，模型输出“超出”；
- 参考断言要求“没有执行”，模型输出“未提交”；
- 合法退款已经成功创建且状态为“待审核”，但回复省略了订单号，仍被不必要地判失败。

另外三条轨迹暴露了“黄金答案不一定黄金”：

- 超额退款在资格判断后停止，没有调用写工具，这比期望“调用后由回调拦截”更安全；
- 多轮会话已有订单信息，模型直接判断资格，没有重复查订单；
- 未支持的“保价”主题不应拿“退款时效”工具代替，也不应向工具传入未支持枚举。

### 第一轮后的修改

1. 业务关键字比较忽略大小写和空白，避免排版造成伪失败；
2. 断言改为稳定业务事实，例如“审批码 + 无效 + 退款”，不绑定“未提交/未执行”的单一措辞；
3. 超额退款的期望轨迹改为只读查询和资格判断，确保高风险写工具根本不被调用；
4. 多轮场景允许复用刚获得的订单上下文；
5. 未支持政策明确要求不调用相近主题工具。

这一步体现了一个重要原则：不能为了提高分数盲目修改 Prompt。先确认失败来自产品、模型、工具还是评估规格。

## 第二轮：找到一个真实 Prompt 缺口

| 指标 | 结果 |
|---|---:|
| 案例通过率 | 84.62% |
| 任务成功率 | 85.71% |
| 工具选择准确率 | 96.43% |
| 回答相似度 | 68.07% |
| 格式合规率 | 100.00% |
| 安全用例通过率 | 100.00% |
| P95 延迟 | 2516.56 ms |
| 估算成本 | $0.018831 |

这一轮全部质量门禁已经通过，但仍有一个真实行为问题：用户问“物流一直不更新怎么办”时，Agent 追问订单号，却没有直接查询一般物流政策。

根因是 Prompt 同时写了“查询规则必须调用工具”和“缺订单号先追问”，没有明确一般政策查询不需要订单号。修订后的规则明确：四类一般政策必须直接查询；只有查询具体订单时才需要订单号。

其余三个失败仍是同义表达导致的断言问题，因此继续把断言收敛到稳定业务事实，没有修改正确的 Agent 行为。

最终 26 个案例、28 个轮次全部通过。ROUGE 没有追求 100%：它只用于发现回复与参考答案是否发生大幅漂移。只要工具轨迹、业务事实、格式和安全约束都通过，合理的自然语言差异不应被当作故障。

## 仍然建议继续做的工作

当前 100% 只说明这 26 个固定案例在本次运行中通过，不代表生产流量没有风险。下一阶段建议：

- 每个核心意图增加更多口语、错别字、长文本和中英文混合改写；
- 对同一模型连续运行多次，统计工具选择的波动，而不是只保存单次结果；
- 用脱敏真实流量补充长尾订单表达和工具失败类型；
- 增加并发、限流、超时、重试和熔断测试；
- 将退款成功判定连接到沙箱支付系统最终状态，而不是只检查回复文本；
- 对高风险动作增加角色权限、审批人身份和审计事件断言；
- 在 ROUGE 之外增加人工抽检或语义 Judge，但不要让同一个被测模型同时充当唯一裁判；
- 保存本报告为发布基线，新模型、Prompt 或工具 Schema 的核心指标下降超过 5% 时回滚。

不同失败结果应该如何修改，见 `README.md` 的“如何阅读结果并修改”章节。

## 如何理解验证边界

- 离线模型只替代网络生成；Runner、工具、数据库、HTTP 和 SkillToolset 仍实际执行。它证明机制接线，不证明自然语言理解质量。
- 在线只做指定冒烟，**没有执行26条数据集的完整在线回归**，也没有重新执行01–09全部付费模型示例。旧 notebook 输出已清除，避免将旧结果当作本轮证据。
- RAG 主线是可解释的词法检索，不是语义向量检索；课程给出可替换接口和向量/混合升级的评估方法。Skills 是 ADK 2.6.3 的实验功能，不等于授权或强制工作流。
- Capstone 默认完整 HTTP 链路的模型是离线替身。在线冒烟为控制费用使用同一服务的业务工具配置；RAG/Skills 在线能力分别验证，未声称完整复合链路已通过在线质量门禁。
- 审批由可信测试入口模拟，无审批 UI；SQLite 账本不执行资金转移，也不替代支付渠道的幂等与对账。公网服务所需的真实 IdP、运维、密钥托管和限流不在该本地教学应用中。
- Docker 实际用于隔离官方 eval 的依赖并验证。主课程的第11章服务 Dockerfile 已收敛构建上下文，但本轮没有另行构建该服务镜像。

## 审查后补充修复

独立审查发现并已修复：知识流程与HTTP服务分离、callback验收未检测工具本体是否执行、身份证X尾号未脱敏、notebook中二级验收进程超时可能遗留子服务。对应行为已纳入真实运行或回归断言。

## 2026-10-18 逐章执行与补充修复

使用项目 `.venv` 与真实 DeepSeek 密钥，将 `google-adk/01`–`15` 逐个 Notebook 连续执行两遍（每章独立内核，执行全部代码格，不按标签跳过）：

- 01–03、05–15 两遍均无异常；08/09 的模型契约断言两次通过。
- 04 的 stdio MCP 格最初报 `ModuleNotFoundError: mcp`：用户 Notebook 实际使用 `D:\Python` 内核，不是项目 `.venv`。安装 `mcp==1.30.0` 后又暴露两个 Windows Jupyter 限制：内核的 `SelectorEventLoop` 不能创建 asyncio 子进程；ipykernel 的 `sys.stderr` 没有真实 `fileno`。该格现改为在独立 Python 进程中运行 `mcp_example/verify.py`，并给 `McpToolset` 传真实 `errlog`。用 `D:\Python` 内核完整执行第 04 章 **0 报错**，MCP 返回 `order_status` 的发现、成功、缺失与关闭结果。
- 离线测试：受限沙箱 61 passed / 4 failed（4 个失败全部来自 asyncio 子进程或 stdio MCP 需要命名管道）；无沙箱 65 passed。
- `practice/c*.py` 共 27 个脚本：26 个通过；`c9_5.py` 仅因沙箱禁止 `asyncio.create_subprocess_exec` 失败。
- 用户内核补装 `mcp==1.30.0`、`rouge-score==0.1.2` 后，`python -m pytest google-adk/eval_example/tests` 18 passed。
